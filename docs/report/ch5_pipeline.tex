\chapter{Processing Pipeline and Identity Learning}

\section{Introduction}

This chapter explains how an uploaded video becomes a set of tracks, identities and analytics. It first describes the end-to-end flow (upload, process, retrieve), then each processing stage, the state models that describe progress, and the configuration parameters that control behaviour.

\section{End-to-End Flow}

\subsection{Upload}

The user posts a video to \code{POST /videos}. The backend saves the file through \code{storage_service.save_upload}, extracts its metadata with \code{extract_video_metadata}, and creates a \code{Video} row with status \code{uploaded}.

\subsection{Process}

A request to \code{POST /videos/{id}/process} first validates that there is no active job for the video. It then creates a \code{ProcessingJob} with status \code{queued}, and either enqueues the work (Celery, when a broker is configured) or runs it synchronously as a background task. Both paths execute the same pipeline in \code{app/services/processing.py}, which performs:

\begin{enumerate}
  \item frame extraction and object detection in a single streaming pass over the video;
  \item tracking, with camera-motion compensation applied before association;
  \item re-identification embeddings and identity consolidation;
  \item analytics computation (\code{compute_video_analytics}).
\end{enumerate}

\add{The detector and the embedding extractor are chosen by the inference mode. In \code{mock} mode a deterministic synthetic detector produces detections for the orchard scenario, which is what makes the development and test runs reproducible. In \code{real} mode the pipeline uses a YOLO detector loaded from \code{YOLO_WEIGHTS_PATH} and, for the embeddings, either the checkpoint at \code{EMBEDDING_MODEL_PATH} or a torchvision ResNet-18 feature extractor as a fallback when that file is absent.}

When processing finishes, the \code{Video} status becomes \code{processed}, and the \code{Track}, \code{DetectionRecord}, \code{FrameTimingRecord}, \code{CameraMotionRecord}, \code{IdentityRecord}, \code{IdentityObservation} and \code{ReidEvent} rows are created.

\subsection{Retrieve}

The GET endpoints return the persisted tracks, identities, analytics, frame timings, motion estimates, ReID events and detections. Retrieval never triggers recomputation.

\section{Status Models}

The progress of a video and of a processing job is described by the shared TypeScript types in \code{packages/types/src/common.ts} and mirrored by the constants of \code{app/models/processing_job.py}:

\begin{itemize}
  \item \code{JobStatus} (processing job): \code{queued} $\rightarrow$ \code{running} $\rightarrow$ \code{completed}, or \code{failed} / \code{cancelled};
  \item \code{ProcessingStage}: \code{uploaded} $\rightarrow$ \code{extracting_frames} $\rightarrow$ \code{detecting} $\rightarrow$ \code{tracking} $\rightarrow$ \code{embedding} $\rightarrow$ \code{memory} $\rightarrow$ \code{reid} $\rightarrow$ \code{analytics} $\rightarrow$ \code{completed} or \code{failed};
  \item the \code{Video} row carries its own status: \code{uploaded}, \code{processing}, \code{processed} or \code{error}.
\end{itemize}

\section{Processing Stages}

\subsection{Frame Extraction}

Frames are read from the uploaded video in a single streaming pass: the pipeline opens the file with \code{cv2.VideoCapture}, processes each frame and releases it immediately, so peak memory does not grow with the length of the video. A per-frame timer feeds the \code{FrameTimingRecord} table and the FPS strip of the interface. The resolution, frame rate and frame count were recorded at upload time, and individual frames are rendered on demand from the video file and cached as JPEG under \code{UPLOAD\_DIR/frames/<video\_id>}. \add{Sub-sampling the frame rate reduces cost on long videos but increases the displacement of fruit between sampled frames, so it directly affects tracker difficulty.}

\subsection{Object Detection}

Fruit are detected in each frame by the YOLO detector in \code{real} mode and by the deterministic mock detector otherwise. Detections below the configured confidence threshold $\tau_{\mathrm{conf}}$ are discarded, and the remainder are persisted as \code{DetectionRecord} rows with their bounding box and confidence. A detection whose confidence falls below the occlusion bound (0.45) is additionally flagged \code{is\_occluded}, which is what the interface later draws as a dashed amber box.

\subsection{Tracking}

The tracker links detections across frames into tracks. Three back-ends are available in the processing pipeline and are selected per job: \code{mock}, \code{bytetrack} and \code{tapnext}; the tracker match threshold $\tau_{\mathrm{match}}$ and the number of buffer frames (how long an unmatched track is kept alive) are configurable. \add{The \code{mock} tracker provides a deterministic centre-distance association for development and tests, ByteTrack is a motion-based tracking-by-detection baseline built on a Kalman filter with two-stage association, and TAPNext follows point queries through the video and is vendored in \code{ml/orchardvision_ml/tracking/tapnext/}.}

\add{When camera-motion compensation is active, the bounding boxes are translated into a stabilised coordinate system before \code{tracker.update} is called and mapped back to raw image coordinates afterwards, so a moving camera does not appear to the tracker as object motion.}

\subsection{Re-Identification Embeddings}

For each tracked detection the pipeline computes an appearance embedding. In \code{real} mode this is either the configured embedding checkpoint or a ResNet-18 feature extractor; in \code{mock} mode a deterministic synthetic embedding is produced. The embeddings feed the identity memory, which compares them with the stored prototypes using cosine similarity and the ReID threshold $\tau_{\mathrm{reid}}$.

\subsection{Identity Consolidation}

Identity consolidation turns tracks and embeddings into persistent identities. For each identity the pipeline stores a prototype embedding, a quality score, the observation count, the first and last frame and an \code{is_confident} flag; every sighting is recorded as an \code{IdentityObservation}. When an identity is lost and later reappears, a \code{ReidEvent} stores the lost frame, the reappearance frame, the similarity and whether the link was accepted, together with the candidate scores that were considered.

\add{Identity numbers are owned by the re-identifier rather than by clustering. The implementation in \code{ml/orchardvision_ml/reid/mock.py} assigns numbers per track chain: a brand-new track receives the lowest unused identity number, unless it is a motion- and appearance-plausible reappearance of a track that was reported lost, in which case it keeps that identity's number. While a track is live its identity never changes, so two boxes visible at the same instant can never share a number; and the number equals the order in which identities were first seen. Candidates for a reappearance are ranked by cosine similarity and then filtered by a motion gate: the reappearing track must lie inside a radius that grows with the length of the occlusion (120\,px at 45\,px per frame by default), which allows slow drift but rejects teleporting matches.}

\add{The prototype $\mathbf{p}_k$ of identity $k$ is updated as a moving average of the embeddings assigned to it, controlled by the memory update rate $\alpha$ and renormalised to unit length:}

\begin{equation}
\colorbox{\phcol}{$\displaystyle \mathbf{p}_k \leftarrow \frac{(1-\alpha)\,\mathbf{p}_k + \alpha\,\mathbf{e}_t}{\left\lVert (1-\alpha)\,\mathbf{p}_k + \alpha\,\mathbf{e}_t\right\rVert_2}$}
\end{equation}

\add{The quality of an observation is the detector confidence, multiplied by 0.55 when the detection is flagged as occluded; observations below a minimum quality (0.3) are dropped before they can influence a prototype. The quality of an identity itself is an exponential moving average of the qualities of its accepted observations, and an identity is marked \code{is_confident} once it has at least three observations and a quality of at least 0.5.}

\subsection{Analytics}

The analytics stage runs \code{compute_video_analytics}, which aggregates the persisted detections, tracks, identities and per-frame timings of one video into the summary served by \code{GET /videos/{id}/analytics}: totals, averages, a count series, a confidence distribution and detection-size bins.

\add{Tracking-quality metrics are computed by a different component. The evaluation harness in \code{ml/orchardvision_ml/evaluation/metrics.py} implements IDF1, HOTA, the number of ID switches, track fragmentation, count error and identity recovery rate against a ground truth, and these are what the experiment endpoints report. The per-video analytics summary currently reports zero for the ID-switch and fragmentation fields, so the interface shows those two as zero for an individual video; the measured values for the experiments are in Chapter~8.}

\section{Camera Motion}

The camera motion of each video is estimated and stored in a single \code{CameraMotionRecord} row per video, holding the motion source, the per-frame displacement, the mean absolute shift, the number of frames analysed, a confidence and whether compensation was applied. The mode is one of the pipeline settings: \code{static} uses the identity transform, \code{drift} simulates a constant handheld translation of half a pixel horizontally and a fifth of a pixel vertically.

\add{Compensating for ego-motion before association keeps motion predictions meaningful when the camera moves along an orchard row. The current estimator is a synthetic model chosen from the setting, so the compensation path is exercised deterministically; a motion estimator computed from optical flow would replace it without changing the interface.}

\section{Identity-Space Visualisation}

The \code{EmbeddingProjection} service reduces identity prototypes to two dimensions with t-SNE or PCA, so that the interface can display them. The coordinates are served by \code{GET /videos/{id}/identities/projection}. \add{Identities of the same fruit should form tight clusters, and well-separated clusters suggest that the ReID threshold is set sensibly.}

\section{Identity Consolidation Procedure}

\add{The listing below restates the consolidation procedure in the order in which the pipeline performs it. It explains the idea rather than reproducing the source.}

\begin{lstlisting}[style=added,language=Python,mathescape=false]
for track in tracks_sorted_by_first_seen:
    if track is a plausible reappearance of a lost identity:
        identity = that_identity            # keep the identity number
        record_reid_event(lost_frame, reappearance_frame,
                          similarity, accepted=True)
    else:
        identity = new_identity(track)       # lowest unused number
    for observation in track.observations:
        if quality(observation) < min_quality: continue   # drop noisy ones
        identity.observation_count += 1
        identity.prototype = moving_average(identity.prototype,
                                            observation.embedding,
                                            memory_update_rate)
        record_identity_observation(identity, observation)
    identity.is_confident = (identity.observation_count >= 3
                             and identity.quality >= 0.5)
\end{lstlisting}

\add{Identity numbers are therefore stable for the whole video and follow first-appearance order. A track that begins after another has ended is compared with the identities that still have an unrecovered lost track; if appearance and motion both permit it, it inherits the identity number and a ReID event is stored. Otherwise a new identity is created. Tracks that overlap in time can never share a number, which is a structural guarantee against merging two simultaneously visible fruit.}

\section{Design Considerations}

\begin{itemize}
  \item \add{\textbf{Threshold trade-off.} A low ReID threshold merges different fruit (undercounting); a high one fragments one fruit into several identities (overcounting). The threshold is therefore exposed as a setting and evaluated through experiments.}
  \item \add{\textbf{Prototype memory.} A small memory update rate makes prototypes stable but slow to adapt to lighting changes; a large one adapts quickly but can drift towards a neighbouring fruit.}
  \item \add{\textbf{Separation of stages.} Persisting detections, tracks, embeddings-derived identities and timings separately makes it possible to diagnose in which stage a counting error originated.}
  \item \add{\textbf{Tracker as a plug-in.} Because the mock, ByteTrack and TAPNext trackers are selected by a setting, a new tracker can be compared with the existing ones using the same video, detector and metrics.}
  \item \add{\textbf{Structural numbering.} Because identity numbers come from track chains rather than from clustering, the over-counting failure mode is excluded by construction; the remaining errors are under-counting from missed re-appearances and false links across long gaps.}
\end{itemize}

\section{Computational Considerations}

\add{Detection and embedding extraction dominate the processing time per frame; association and identity matching grow with the number of active tracks and identities. The per-frame timing records stored for each video allow these costs to be measured on the actual hardware, which is the basis of the runtime study in Chapter~8.}

\section{Failure Handling}

\add{A processing job can end in the \code{FAILED} state, and the corresponding video in the \code{error} state, for example when the video cannot be decoded or a stage raises an exception. Because every stage persists its output, the cause of a failure can be located from the \code{stage} recorded on the job. A failed video can be deleted with \code{DELETE /videos/{id}} and uploaded again after the problem is fixed.}

\section{Reproducibility}

\add{Each \code{ProcessingJob} stores the configuration it ran with in its \code{config} dictionary, and each experiment stores its tracker, scenario and number of frames together with the resulting metrics. Together with the exports in JSON or CSV, this makes it possible to repeat an evaluation and to attach the exact configuration to every number reported in Chapter~8.}

\section{Concurrency and Job Control}

A video can have only one active processing job: requesting processing while a job is active is rejected (\add{the API defines a \code{ConflictError} for this kind of situation}). The state of a job (\code{status}, \code{stage}, \code{progress}) can be polled through \code{GET /jobs/{id}}. When the work is enqueued through Celery it runs outside the API process; otherwise it runs as a background task of the API process.
